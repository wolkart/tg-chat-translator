# Design

## Context

Шаг 1 работает так. Владелец пишет в чате с ботом, `routeOwnerMessage` (`src/owner/routing.ts`)
ищет адресата: тема → ответ на сообщение бота → единственный активный → «Кому?» → «Не понял,
кому». Найденному разговору отвечает `sendOwnerReply`
(`src/channels/private-chat/outgoing.ts`): перевод, проверка, отправка через подключение. На
любой отказ в теме появляется `renderNotSent(<сырая причина>, перевод)`. Сообщения из лички
идут конвейером `incomingSteps` (`src/channels/private-chat/incoming.ts`): язык → разговор →
перевод → доставка. Разговор начинает только собеседник на чужом языке. Ошибка провайдера —
`TranslationError` с телом ответа в тексте (`src/translate/llm.ts`).

Из живых проверок:
- отказы Telegram различимы: `BUSINESS_PEER_USAGE_MISSING` — правило суток,
  `BUSINESS_PEER_INVALID` — чата нет среди чатов бота (2026-10-11);
- inline-кнопка «Отправить через бота» работает только в сообщениях самого бота, не в
  сообщениях от имени владельца. Наши темы подходят;
- `business_message` приходит и на собственные сообщения владельца в личке.

Пока не проверено: приходит ли боту `business_message` на сообщение владельца,
отправленное через inline-режим, и есть ли в нём `via_bot`.

## Goals / Non-Goals

**Goals:**
- один модуль ручной отправки для двух входов, «Написать первым» и «Не отправлено»: черновик,
  кнопки, ответ на inline-запрос, узнавание отправленного черновика;
- причины отказа и ошибки провайдера — таблицами: новый код означает новую строку, а не `if`
  по месту;
- маршрут меняется только в одном месте — в цепочке `routeOwnerMessage`.

**Non-Goals:**
- `chosen_inline_result` не используем: нужна лишняя настройка в BotFather (inline feedback),
  а сам факт отправки и так приносит `business_message`;
- нет предпросмотра «@бот текст» в чужом чате с переводом на лету: модель вызывалась бы на
  каждую паузу в наборе;
- вложения через inline (`InlineQueryResultCached*`) не отправляем: по спеке первым уходит
  только текст.

## Decisions

### 1. Черновик — запись в базе, в inline-запросе только её номер

Таблица `drafts`: `id`, `owner_id`, `conversation_id` (NULL для нового собеседника),
`original`, `translation` (с обрезанными пробелами по краям), `created_at`. Кнопка —
`switch_inline_query_chosen_chat` с `query: "<id>"` и `allow_user_chats: true` (только
личные чаты с людьми). На `inline_query` от владельца бот ищет черновик по паре
`(owner_id, id)` и отвечает одним `InlineQueryResultArticle`:
- `message_text` — перевод, без `parse_mode`: у собеседника он выглядит как обычный текст;
- `title` — начало перевода, `description` — «Нажмите — уйдёт от вашего имени»;
- `is_personal: true` и `cache_time: 0`, иначе Telegram отдал бы закэшированный ответ
  другому человеку, набравшему тот же номер.

Черновика нет или он истёк — пустой список и `button` с текстом «Перевод устарел — напишите
заново» и `start_parameter: "draft"`. Он открывает чат с ботом, а `/start` с параметром
показывает статус.

*Почему не перевод прямо в query:* лимит запроса — 256 символов, и текст был бы виден в поле
ввода. Через `callback_data` от имени владельца не отправить вовсе. Номер черновика можно
угадать, но ответ получает только владелец.

Срок черновика — 7 дней (`store.cleanup`). Это допущение: кнопка под «Не отправлено» остаётся
в теме надолго, а неделя покрывает «вернусь к этому завтра-послезавтра». Минимум данных
соблюдён: в черновике только текст владельца и перевод.

### 2. Кнопки — расширение `InlineButton`

`InlineButton` в `src/telegram.ts` становится объединением:
- `{ text, data }` — как сейчас;
- `{ text, copy }` → `copy_text`;
- `{ text, chooseChat }` → `switch_inline_query_chosen_chat`.

У любой кнопки есть необязательный `style: 'success' | 'primary' | 'danger'`. Преобразование
в формат Bot API — в `other()`, как сейчас. «Отправить через бота» — `success` (зелёная,
главное действие экрана, по решению 2026-10-11), «Скопировать» — без цвета. Раскладка — две
строки: на телефоне длинная зелёная кнопка во всю ширину не обрезается.

### 3. Модуль `src/owner/manual-send.ts`

В модуле:
- `newPeerDraft(deps, payload)` — вход «Написать первым»: перевод на язык собеседника из
  пары, проверка `direction: 'outgoing'`, запись черновика, ответ владельцу с кнопками;
- `renderDraft(head, translation)` и `manualKeyboard(draft, { inline, media })` —
  оформление и кнопки;
- `answerInline(deps, query)` — ответ на inline-запрос.

Вход «Не отправлено» (`notSent` в `outgoing.ts`) берёт те же `renderDraft` и
`manualKeyboard`: перевод там уже есть и уже проверен, черновик только записывается. Для
нового собеседника история пустая: модели нечего брать из разговора, а подмена из истории
невозможна.

Оформление:
- **новый собеседник**: `<i>Перевод для нового собеседника (английский):</i>` и перевод,
  ответом на сообщение владельца, вне тем;
- **перевод длиннее 256 символов**: кнопки «Скопировать» нет, перевод — в `<pre>`, над ним
  «Нажмите на перевод, чтобы скопировать». Копируется ли `<pre>` нажатием на телефоне и на
  Mac — проверяется вживую (запасной вариант — `<code>`);
- **перевод длиннее 4096 символов**: в одно сообщение через inline не влезает, поэтому
  кнопки «Отправить через бота» нет. Перевод показывается частями, каждая копируется
  нажатием. Для первого сообщения это редкость;
- **подозрительный перевод или перевод не удался**: без кнопок, тексты из спеки.

`Topics.postText` получает необязательную клавиатуру: она вешается на последнюю часть.

### 4. Отказы — таблица причин

Отказы описаны таблицей `SEND_REFUSALS` в `src/channels/private-chat/refusals.ts` (имя
`REFUSALS` уже занято шаблонами отказа модели в `check.ts`), строка на код:
- `match` — регулярка по `description`;
- `text(peerName)` — понятная причина. Без рода: «от Timon давно не было сообщений», а не
  «давно не писал» — собеседник может быть и Maria.

Две строки (`BUSINESS_PEER_USAGE_MISSING`, `BUSINESS_PEER_INVALID`) плюс запасной текст
«Telegram не принял сообщение — <слова Telegram>». Любая строка таблицы — окончательный отказ
подключения (`isFinalRefusal`): повтор с загрузкой заново ничего не даст. Там же тексты
заранее известных случаев: `NO_REPLY_RIGHT` и `BOT_DISCONNECTED`.

Заранее известные случаи — бот отключён и нет `canReply` — проверяются до отправки, по
порядку «отключён → нет права → холостой прогон → отправка»: в холостом прогоне без права
отвечать «ушло бы» не появляется.

Лестнице вложений передаётся `rethrow: isFinalRefusal`. Окончательный отказ выходит из неё
исключением и в `sendOwnerReply` разбирается той же таблицей, а вторая ступень (скачать и
загрузить) не пробуется.

*Почему таблица, а не `switch`:* коды отказов Telegram добавляются от версии к версии. Новый
код означает новую строку, а тест таблицы — один на все.

### 5. Маршрут: «Кому?» при любом числе активных, без активных — черновик

В `routeOwnerMessage` два изменения: `active.length >= 1` → `choose`, `0` → новый вид
`{ kind: 'new' }`. `NO_TARGET` уходит.

`chooseKeyboard` добавляет «Новому собеседнику» (`new:<pendingId>`), только если в
отложенном сообщении есть текст и нет вложения. `parseChoice` узнаёт `new`. `onChoice`
забирает отложенное тем же одним запросом (повторное нажатие ничего не найдёт), правит
вопрос на «Новому собеседнику» и вызывает `newPeerDraft` ответом на исходное сообщение.

Решение автора 2026-10-12 (proposal, BREAKING): живую проверку «вне темы при одном активном —
уходит, ✓ Timon» сменяет «Кому?». Тесты маршрута правятся под спеку.

### 6. Отправка через бота заводит разговор — новый шаг конвейера

`parseBusinessMessage` отмечает в реплике `viaBot: message.via_bot?.id === botId`. Новый шаг
`черновик` стоит перед шагом `разговор`. Для `owner-direct` с текстом он ищет черновик
владельца с таким же переводом за срок жизни черновиков. Сравниваются строки с обрезанными
пробелами по краям и `\r\n` → `\n`.

Дальше:
- шаг `разговор`: если разговора нет, `owner-direct` и `viaBot` — разговор заводится с
  `lastPeerAt = 0`. До ответа собеседника он не активен и в «Кому?» не попадает;
- шаг `доставка`: при найденном черновике — `renderSent(оригинал, перевод)` и реплика в
  истории `{ role: 'owner', original, translation }`; иначе — как раньше, «Вы в личке».

*Почему разговор заводит только `viaBot`, а не совпадение текста:* короткий черновик
(«OK», «Thanks!») совпал бы с обычным сообщением другу, и у друга появилась бы тема. В
начатом разговоре совпадение текста безвредно, поэтому вставленный руками перевод там
узнаётся.

`createConversation` получает `lastPeerAt` явно: сейчас туда пишется `now`.

### 7. Inline-запрос в `app.ts`

- новая строка в реестре обработчиков: `inline-запрос` → `answerInline`;
- фильтр постороннего смотрит и на `update.inline_query?.from`. Постороннему бот не отвечает
  вовсе: ни сети, ни записи в базе, Telegram покажет пустоту;
- `allowed_updates` в `main.ts` — плюс `inline_query`;
- в `TelegramApi` — `answerInline(queryId, articles, { button? })`. Флаги
  `is_personal: true, cache_time: 0` выставляются внутри, и забыть их нельзя;
- список апдейтов — константа `ALLOWED_UPDATES` в `app.ts`, тест проверяет, что в нём есть
  `inline_query`: без него кнопка молча не работает.

### 8. Inline Mode: проверка при старте и самовосстановление

`BotInfo.supportsInlineQueries` берётся из `getMe`. `startupChecks` отправляет общее
сообщение `INLINE_OFF` (ключ `botfather:inline`).

В `Deps` — `inlineEnabled(): Promise<boolean>`. Пока Inline Mode включён, это значение из
памяти. Пока выключен, при каждом новом черновике бот снова спрашивает `getMe`, но не чаще
раза в минуту. Тогда включение в BotFather бот замечает без перезапуска (спека), а лишних
запросов нет.

*Почему кнопку не показывать при выключенном режиме:* как Telegram примет сообщение с такой
кнопкой у бота без inline-режима, не проверено. Если он отвергнет сообщение целиком,
пропадёт и перевод.

### 9. Ошибки провайдера — таблица по коду

`PROVIDER_ERRORS` в `src/translate/errors.ts` — строки «условие на статус → причина
(provider) и подсказка (provider)»:

| Код | Причина | Подсказка |
|---|---|---|
| 401 | `<label>: ключ не подходит` | `Проверьте <envKey> в .env — ключ берут здесь: <keysUrl>` |
| 402 | `<label>: на балансе закончились деньги` | `Пополните баланс у <label>.` |
| 429 | `<label> просит подождать — слишком много запросов` | `Обычно это проходит само за минуту-другую.` |
| 5xx | `<label> временно не работает` | `Обычно это проходит само — подождите.` |
| другое | `<label> ответил ошибкой <код>` | `Проверьте ключ и баланс у провайдера.` |

Ещё три случая:
- ответ 200 с `error` в теле (так бывает у OpenRouter): берётся `error.code`, если он
  числовой, иначе «<label> вернул ошибку»;
- таймаут — как сейчас;
- нет сети — «нет связи с <label>».

`TranslationError` получает поля `hint` и `detail` (сырое тело). `detail` пишется в консоль
через `alerts.log`, где уже работает замена секретов. `alertModelFailure` берёт подсказку из
ошибки. В `createTranslator` вместо `label` передаётся провайдер целиком — нужны `envKey` и
`keysUrl`.

### 10. Путь к настройке — две константы

В `connection.ts`:
- `SETTINGS_PATH` — «Настройки → Аккаунт → Автоматизация чатов (на Mac — Настройки →
  Изменить профиль → Автоматизация чатов)»: где подключить бота;
- `BOT_SETTINGS_PATH` — то же с «→ этот бот»: где права уже подключённого.

Ими пользуются `NO_REPLY`, `DISABLED`, `connectionLine`, строка права в `statusText` и тексты
отказов. В статус добавляется строка «Написать первым: …».

## Risks / Trade-offs

- **[Риск] `business_message` на отправку через inline не приходит или приходит без `via_bot`**
  → код шага 6 пишется по документации Bot API (`Message.via_bot`) на образце, собранном
  вручную. Живая проверка начинается с разведки: снимает настоящий образец и сверяет с ним.
  Если поля нет — стоп и вопрос автору: на кону требование «Отправка через бота заводит
  разговор». Так живой сеанс с автором один, а переделка, если понадобится, касается одного
  шага конвейера.
- **[Риск] Чат не среди чатов бота** («Только выбранные чаты») → перевод уходит, а тема не
  появляется, и ответ собеседника бот не увидит. Это ограничение платформы, оно записано в
  спеке. В README — совет «Все личные чаты, кроме…». У тестового бота сейчас «Только
  выбранные — Timon»: на живой проверке нужен второй чат в списке.
- **[Компромисс] Лишнее нажатие в ленте «Все»** при одном активном разговоре → решение
  автора. «Ответить» и ответ в теме работают без вопроса.
- **[Риск] `<pre>` не копируется нажатием на каком-то клиенте** → проверка на телефоне и на
  Mac. Запасной вариант — `<code>`, на поведение это не влияет.
- **[Компромисс] Любой текст вне тем без активных разговоров стоит вызова модели** (например,
  случайная команда) → копейки. Команды кроме `/start` — забота панели (шаг 5, `BACKLOG.md`).
- **[Риск] Пометка «via @бот» видна собеседнику** → так устроен inline-режим, автор это
  принял. Ответ собеседника снова уходит обычным сообщением владельца.

## Migration Plan

- Новая таблица `drafts` — `CREATE TABLE IF NOT EXISTS`: старая база открывается как есть,
  данные не переносятся.
- BotFather: Inline Mode у тестового бота уже включён. Покупатель узнает о нём из
  сообщения при старте и из УСТАНОВКИ (шаг 6).
- Откат: прошлая версия кода таблицу `drafts` просто не читает.
- После архивации — поправить «Маршрутизация ответа» в `CLAUDE.md` продукта.

## Open Questions

- Как в «Автоматизации чатов» называется список чатов бота («Доступ к чатам»?) — уточнить
  на живой проверке и при желании дописать в текст отказа `BUSINESS_PEER_INVALID`. Поведение
  и задачи от этого не меняются.
