# Design

## Context

Сейчас настройки собираются один раз, при старте:
- `main.ts` читает из базы пару языков и модель, ключ — из `.env`, через `loadSettings`
  (`src/startup.ts`);
- кладёт в `Deps` готовые `languages`, `translator` и `translatorInfo`;
- шаги берут их оттуда: `incoming.ts`, `outgoing.ts`, `manual-send.ts`, `statusText` в
  `app.ts`.

Поменять что-то без перезапуска нельзя. По `/start` выводится текст `statusText`. Нажатия
кнопок умеет разбирать только «Кому?» (`onChoice`). `startupChecks` проверяет BotFather
тремя `if`. Замена секретов (`createScrubber`) знает только значения из `.env`.

Образец панели — `news-reposter/src/panel.ts`: одно сообщение правится на месте, строка
«что произошло» сверху, ключ показывается огрызком, сообщение с ключом удаляется. Но там
панель живёт на глобальных переменных и ходит в grammy напрямую. Здесь всё идёт через
`TelegramApi` и `Deps` — ради тестов на подделках и ради нескольких владельцев в будущем.

Что выяснили до спеки живыми запросами 2026-10-15 (ключ и бот автора):
- `GET /api/v1/key` отдаёт `limit`, `limit_remaining`, `usage_daily`, `usage_monthly` и
  `expires_at`;
- `GET /api/v1/credits` отвечает 200 обычному ключу, хотя документация требует ключ
  управления;
- `GET /api/v1/models` открыт без ключа и отдаёт цены и `expiration_date`. У
  `google/gemini-2.5-flash` там 2026-10-20;
- в ответе чата OpenRouter всегда есть `usage.cost`;
- `getMe` бота отдаёт `allows_users_to_create_topics`.

## Goals / Non-Goals

**Goals:**
- изменение в панели действует со следующего перевода: настройки читаются в момент вызова;
- разделы панели, строки состояния, проверки BotFather, предупреждения и команды — реестры.
  Платный раздел («Голосовые», «Глоссарий») встаёт новой строкой, ядро не правится;
- все настройки — по `ownerId`: одна программа сможет обслуживать многих.

**Non-Goals:**
- нет фактического учёта цены каждого перевода: `usage.cost` не сохраняем, цена — оценка;
- нет шифрования ключа в базе — почему, в «Рисках»;
- нет «Удалить ключ»: замена ключа закрывает и утечку, и истёкший ключ, а удаление без
  замены просто останавливает переводы. Поэтому красных кнопок в этом изменении нет;
- нет `chosen_inline_result` и вебхуков.

## Decisions

### 1. Настройки — функция, а не готовые значения в Deps

`Deps.languages`, `languagesProblem`, `translator`, `translatorProblem` и `translatorInfo`
заменяет `config(ownerId): Config`. Она каждый раз собирает из базы и `.env`:
- пару языков или причину, почему её нет;
- обращение;
- провайдера, модель и откуда ключ (`env` или `panel`);
- готовый переводчик (замыкание `createTranslator`).

Это несколько чтений SQLite по ключу — микросекунды на перевод.

Альтернатива — кэш, который сбрасывается при сохранении в панели. Отвергнута: появляются два
источника правды, а забытый сброс даёт ровно ту поломку, которую тесты не ловят. `ownerId`
в сигнатуре — ради нескольких владельцев: входящее уже несёт `replica.ownerId`.

Как это меняет остальное:
- `loadSettings` превращается в `config`;
- стартовые проверки берут из неё проблемы с языками и моделью;
- `translatorUnavailable` читает их же;
- в тестах `setupDeps` получает `config` из подделок, а сценарий «пару сменили — следующий
  перевод по новой» проверяется сменой настройки в базе между двумя сообщениями.

### 2. Ключи — в той же таблице settings, `.env` главнее

Ключ из панели хранится в `settings` под `key:<id провайдера>`. Ключи для
`resolveModel` — `{ ...ключи из базы, ...ключи из .env }`: значение из `.env` перекрывает.
`resolveModel` возвращает и источник ключа. От источника зависят:
- подсказка к ошибке 401 (`describeProviderError` получает источник): «Вставьте ключ
  заново: /start → 🔑 Ключ» или «Проверьте OPENROUTER_API_KEY в .env»;
- «🔒 задан в .env» на экране ключа;
- текст предупреждения о сроке.

Запасной путь из шага 1 остаётся: у выбранного провайдера ключа нет, а у другого есть —
работает тот, у кого есть. Это нужно установке, где ключ вписан только в `.env`.

Замена секретов становится пополняемой: `createScrubber` возвращает функцию с методом
`add(value)`. При старте туда добавляются все ключи из базы. Присланный ключ добавляется
**до** проверки, даже если его потом отвергнут: ответ провайдера на неверный ключ иначе
мог бы процитировать его в консоль.

### 3. Панель — реестр разделов

Модули в `src/owner/panel/`:
- `screen.ts` — типы экрана, контекста и раздела, данные кнопок;
- `status.ts` — реестр строк состояния;
- `panel.ts` — открытие, разбор нажатий, сбор контекста и кэш счёта;
- `key-input.ts` — ожидание ключа, путь ключа и страховка;
- `sections/` — по файлу на раздел и реестр `sections/index.ts`.

Раздел — это `{ id, button, render(ctx, env), act? }`. Кнопки главного экрана строятся по
реестру, по две в ряд. Строки состояния — тоже реестр функций `(ctx) => Line | null`:
- подключение;
- BotFather;
- ключ;
- языки;
- обращение;
- модель;
- «Написать первым»;
- холостой прогон.

У строки есть флаг «проблема». По первой проблеме главный экран делает зелёной кнопку
раздела, который её чинит.

`ctx` собирается один раз на отрисовку: `config`, подключение из базы, свежий `getMe` и
снимок счёта провайдера (решение 6). Экран — `{ html, keyboard }`, все подставляемые части
проходят `escapeHtml`, даже названия из кода.

Данные кнопок — `p:<раздел>:<действие>[:<аргумент>]`, не длиннее 64 байт:
- язык — по коду;
- провайдер — по id;
- модель — по номеру в списке, потому что в id моделей бывают «:» и «/».

Тест обходит все экраны и проверяет длину каждой кнопки. Нажатия разбирает реестр в
`app.ts`: префикс `p:` уходит панели, `to:`, `new:` и `cancel:` — «Кому?», как раньше.

Переход по экрану — `editText` того же сообщения. `TelegramApi.editText` получает
необязательные `{ html, keyboard }`, старые вызовы не меняются. Ответ Telegram «message is
not modified» глотается. Если это было «🔄 Обновить», всплывает «Без изменений».
Состояния в данных кнопок нет, кроме ожидания ключа. Поэтому старая панель работает и
после перезапуска.

### 4. `getMe` при каждом показе главного экрана

Проверки BotFather — таблица `BOTFATHER_CHECKS`: ключ оповещения, `ok(me)`, текст для
старта и строка для панели. `startupChecks` проходит по ней, а не тремя `if`.
`BotInfo` получает `allowsUsersToCreateTopics`.

Главный экран (открытие, «← Назад», «🔄 Обновить») каждый раз спрашивает `getMe`. Это один
лёгкий запрос, и только по действию владельца. Результат передаётся в проверку Inline Mode:
`createInlineCheck` получает `update(enabled)`. Так бот замечает и выключение после старта
(требование `manual-send`), а не только включение.

### 5. Ожидание ключа — в памяти, страховка — по виду ключа

После «Вставить ключ» в памяти хранится `Map<ownerId, { providerId, until, switchProvider }>`
на 10 минут. Ожидание снимают «Отмена», любое нажатие кнопки панели и `/start`.

`onOwnerMessage` проверяет по порядку:
1. Команда. `entities[0]` типа `bot_command` со смещением 0, имя без `@бот`. Реестр команд
   `{ start: панель }`, на остальные — «Такой команды нет…». Ответ — в ту же тему.
2. Бот ждёт ключ, и сообщение пришло вне тем. Похоже на ключ этого провайдера — путь ключа.
   Похоже на ключ другого провайдера — удалить, в замену секретов, не сохранять, сказать, что
   ключ чужой (решение автора 2026-10-15). Не похоже ни на какой ключ — подсказка, как ключ
   выглядит.
3. В тексте или подписи есть ключ любого провайдера по виду. Сообщение удаляется и не
   переводится, бот подсказывает, как сохранить ключ.
4. Обычный маршрут: тема → ответ → «Кому?» → новый собеседник.

Вид ключа — поле `keyPattern` в таблице провайдеров:
- OpenRouter — `sk-or-v1-` и 64 шестнадцатеричных знака;
- DeepSeek и Moonshot — `sk-` и не меньше 32 знаков;
- Groq — `gsk_` и не меньше 40.

У локальной модели шаблона нет, ей подходит любой текст в ожидании. Шаблоны длинные и
специфичные, поэтому «sk-board» в обычной фразе не срабатывает. Тесты — на синтетических
ключах нужной формы, реальных ключей в репозитории нет.

Почему память, а не база. Если бот перезапустится посреди ожидания, следующее сообщение не
будет принято за ключ. Но ключ по виду всё равно поймает пункт 3: он не уйдёт ни модели, ни
собеседнику. Запись в базе ради 10-минутного состояния — лишняя таблица и лишняя чистка.

Путь ключа:
1. добавить ключ в замену секретов;
2. удалить сообщение (`deleteMessage`). Не вышло — сказать удалить самому;
3. проверить у провайдера;
4. сохранить, если нужно — переключить провайдера, снять ожидание;
5. прислать новую панель с итогом.

Проверка ключа — `account.verify` у провайдера. Если её нет — `GET {baseUrl}/models` с
ключом: 2xx — принят, 401 — не принят, иначе — «не проверить». 403 — тоже «не проверить»:
так отвечают и на верный ключ, если провайдер закрыт из страны (ревью ветки 2026-10-15). У OpenRouter своя
проверка, `GET /api/v1/key`: его `/models` открыт без ключа и принял бы любую строку. Это
подводный камень, в комментарии — почему. Тайм-аут проверки — 10 секунд.

### 6. Счёт OpenRouter — отдельный модуль за полем таблицы провайдеров

`src/translate/openrouter.ts`, поле `account` в строке OpenRouter. Типы счёта, общая проверка
ключа и `createAccounts` — в `src/translate/account.ts`. У остальных провайдеров
поля нет, и экран баланса показывает ссылку на их кабинет (`keysUrl`). Что внутри:
- `verify(key)` — `GET /api/v1/key`;
- `balance(key)` — параллельно `GET /api/v1/key` и `GET /api/v1/credits`;
- `prices()` — `GET /api/v1/models`, кэш в памяти на час. Цены меняются редко, а список
  моделей OpenRouter — сотни записей.

Как считается баланс:
- остаток — меньшее из `limit_remaining` и `total_credits − total_usage`;
- `limit: null` — у ключа лимита нет;
- `/credits` ответил 403 — остаток только по лимиту ключа, с пометкой;
- нет ни того, ни другого — «остаток не узнать».

Снимок счёта для панели кэшируется на 60 секунд: хождение по экранам не дёргает OpenRouter
на каждое нажатие, а «🔄 Обновить» берёт свежий. Разбор ответов терпит пропавшие поля.
Хуже, чем «не узнать», он не ошибается, и на перевод не влияет.

Запросы идут только на адреса из таблицы провайдеров. От владельца панель адресов не
принимает, поэтому SSRF-фильтру проверять нечего: `LOCAL_BASE_URL` задаёт сам владелец в
`.env`. `fetch` передаётся параметром. Тесты идут на сохранённых образцах `/key`, `/credits`
и `/models` из живых ответов 2026-10-15: у `/key` вырезаны `label` и id, `/models` сокращён
до наших моделей и одной с `expiration_date`.

### 7. Цена перевода — оценка по типичному запросу

Цена одного перевода = цена входа × `TYPICAL_INPUT_TOKENS` + цена выхода ×
`TYPICAL_OUTPUT_TOKENS`. Константы снимаются один раз живым запросом: `buildPrompt` с
историей из 10 реплик и обычным сообщением, `usage.prompt_tokens` и
`usage.completion_tokens` из ответа OpenRouter. Число, дата и способ замера — в
комментарии. Замер 2026-10-15 (Haiku 5.5, три запроса): на вход 1426 (входящее на русский, с
примерами), 881 (ответ на английский) и 997 (он же на «вы»), на выход — 26–42. Взято с
запасом: 1200 и 40, у Haiku это ≈ $0,14 за 1000 переводов. На экранах — «≈», цены за 1000 переводов. «Хватит на» — остаток, делённый на
цену, с округлением до двух значащих цифр.

Альтернатива — среднее по фактическому `usage.cost` из ответов. Она точнее, но меняет
договор `Translator` (он возвращает строку) и требует хранить траты. Отложено: для показа и
для решения «хватит ли денег» оценки достаточно.

### 8. Предупреждения — реестр, раз в сутки по дате в базе

Реестр `ACCOUNT_WARNINGS`: `{ kind, text(input) → текст | null }`, где input — провайдер,
источник ключа, название модели, баланс, цена модели и текущее время. Тот же реестр даёт
строки «⚠️» на экране баланса. Виды:
- `key-expiry` — срок ключа, 3 дня;
- `low-balance` — меньше $1. Текст зависит от того, что меньше: счёт или лимит ключа;
- `model-leaving` — `expiration_date` текущей модели, 14 дней.

Проверка идёт при старте и дальше каждые 6 часов (`setInterval`, `unref`, как чистка
базы). Отправленное предупреждение записывает в `settings` `warned:<kind>` = дату по UTC.
В тот же день оно не повторяется, в том числе после перезапуска. На следующий день, если
причина осталась, приходит снова.

Почему 6 часов, а не сутки. Интервал в 24 часа, запущенный в 23:00, перешагнул бы
следующий день. Дата в базе не даёт частой проверке заспамить. Отправка — через
`alerts.notify`: своя суточная защита есть, 10-минутная не нужна. `notify` возвращает,
дошло ли сообщение: недошедшее не отмечается отправленным, следующая проверка повторит. Работает только у
провайдеров с `account`.

### 9. Обращение — фрагмент промпта по запросу

`TranslateRequest` получает `address: 'as-is' | 'formal'`. `PromptFragment` вместо
`(target)` получает весь запрос и может вернуть `null`. Реестр — `[BASE_FRAGMENT,
ADDRESS_FRAGMENT]`. Напоминание об изоляции по-прежнему последнее.

`ADDRESS_FRAGMENT` пишет текст только для `formal`, по-английски, как остальной промпт.
Смысл: где у языка есть вежливое «вы» (Sie, vous, usted, Lei, вы), обращаться так, даже
если оригинал на «ты»; регистр вежливый и нейтральный; меняется только звучание — без
приветствий, благодарностей и извинений, которых нет у автора; короткое остаётся коротким.

Правка после живой проверки 2026-10-15: на «ок» при `formal` Haiku выдала объяснение вместо
перевода, и оно ушло собеседнику. Замер (10 фраз × 2 языка × 2 модели × 3 прогона): у прежнего
фрагмента 3 подозрительных ответа из 120 («Formal "Sie" required…»), варианты без прямой команды
теряли «Sie» у Haiku. Итог — два изменения. При `formal` строка базовой инструкции «Keep the form of
address used in the conversation» заменяется строкой про вежливое «вы», чтобы два указания не
спорили. Во фрагмент добавлено «Do this silently: … no notes about the form of address». На итоговом
варианте — 0 подозрительных из 240, «Sie» 36 из 36. Вторым слоем проверка перевода получила правило
«пояснение модели» (спека `translation`).

`address` из `config` передают ответ владельца (`sendOwnerReply`) и «Написать первым»
(`newPeerDraft`). Входящее всегда передаёт `as-is`.

Проверка ответа (`check.ts`) не меняется. Вежливый ответ длиннее, но правило «слишком
длинно» действует только с 30 букв и при 2,5-кратной разнице.

### 10. Модели — объекты с названием

`Provider.models` становится `{ id, title, note? }[]`. Список OpenRouter — из спеки
`translation`. Пометки взяты из замера 2026-10-12, у DeepSeek V4 Flash — «самая дешёвая».
Новый замер на итоговом списке — шаг 6, он же уточнит пометки.

`resolveModel` сравнивает по `id`. Сохранённая модель, которой нет в списке, заменяется
первой — так было и раньше.

У других провайдеров список не трогаем: в рилсе и в установке по умолчанию OpenRouter.

### 11. Тексты BotFather — по мини-приложению

Пути пишутся как «@BotFather → Open → этот бот → Bot Settings» и название переключателя.
Secretary Mode и Inline Mode сверены 2026-10-14. Threaded Mode и переключатель создания тем
пользователями сверяются на живой проверке по скриншоту экрана. Если имена другие, правятся
только строки таблицы `BOTFATHER_CHECKS`.

## Risks / Trade-offs

- **[Ключ лежит в базе открытым текстом]** → файл базы лежит рядом с `.env`, права у них
  одни. Шифрование ключом, который лежит там же, ничего не даёт. README (шаг 6) скажет, что
  база — такой же секрет, как `.env`.
- **[Ключ секунду виден в переписке до удаления]** → удаляется первым действием, до
  проверки. Сообщение своё, пуша о нём нет. Не удалилось — бот просит удалить руками.
- **[`/credits` по документации требует ключ управления, и OpenRouter может начать это
  применять]** → 403 разбирается: остаток по лимиту ключа с пометкой «баланс счёта этим
  ключом не виден».
- **[OpenRouter изменит формат ответов]** → разбор терпит пропуски и показывает «не узнать».
  Перевод от этого модуля не зависит.
- **[Ожидание ключа теряется при перезапуске]** → ключ по виду не переводится и не уходит
  (решение 5), владелец просто нажмёт «Вставить ключ» ещё раз.
- **[Оценка цены расходится с фактом на длинной истории]** → знак «≈», константы сняты на
  средней истории. Фактический учёт — отдельным изменением, если понадобится.
- **[Шаблон ключа сработает на обычном тексте]** → шаблоны длинные (32+ знаков после
  префикса), сценарий «sk-board» в тестах.
- **[Смена пары посреди разговоров]** → новые переводы идут по новой паре, темы остаются.
  Разные языки у разных собеседников — платная версия («язык по собеседнику»).
- **[Ссылка пополнения `https://openrouter.ai/settings/credits` не подтверждена: без входа
  страница уводит на вход]** → сверяется на живой проверке. Ссылка лежит в таблице
  провайдеров одной строкой.

## Migration Plan

- База: новые ключи `settings` — `address` (дефолт `as-is` через `ensureDefaults`),
  `key:<провайдер>`, `warned:<вид>`. Схема таблиц не меняется. У тестового бота сохранена
  `anthropic/claude-haiku-5.5` — она остаётся в списке.
- `.env.example`: у `OPENROUTER_API_KEY` — «можно не заполнять: ключ вставляется в боте,
  /start → 🔑 Ключ».
- Откат: старый код новых ключей настроек не читает. Ключ, вставленный в панели, старой
  версии не виден — его придётся вписать в `.env`.
